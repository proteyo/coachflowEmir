# Исправления 4 ноября 2026

Канонические исходники frontend находятся в `expo/`, теперь на SDK 58. Локальный `preview-sdk58` — копия для запуска, обновляемая командой `npm run preview:sync` из `expo`. Исходники исправляются в репозитории. Секреты и `.env` эта команда не копирует.

## Изменения

- Регистрация не заменяет пароль и имя существующего неподтверждённого аккаунта и не рассылает письма повторным вызовом. При подтверждении email владелец задаёт пароль вместе с кодом: чужой пароль, заданный до подтверждения, перестаёт действовать.
- Общие атомарные лимиты запросов хранятся в PostgreSQL и работают между процессами: вход, регистрация, коды и восстановление. Ограничения используют хешированные идентификаторы и удаляют истёкшие записи.
- Access-токены связаны с серверной сессией. Refresh-токены ротируются и проверяются по хешу; повторное применение старого токена запрещено. Выход отзывает эту сессию, сброс пароля — все сессии пользователя. После обновления потребуется повторный вход.
- Новые пароли используют bcrypt-SHA256, существующие обычные bcrypt-хеши поддерживаются. Для старого bcrypt-пароля длиннее 72 байт требуется восстановление: старый хеш не позволяет надёжно отличить отброшенный суффикс.
- Кеш frontend разделён по user ID. Общий старый кеш удаляется, поскольку его владельца нельзя надёжно определить. Поздние ответы и устаревшие обработчики прежнего аккаунта отбрасываются; logout удаляет кеш текущего аккаунта. Несинхронизированные данные старого общего кеша автоматически не переносятся.
- DataContext использует сессию AuthContext, а не устаревший ключ AsyncStorage. Обновление токена не сбрасывает кеш аккаунта.
- Отправка сообщений и WebSocket требуют связи клиента с тренером. История собственных переписок остаётся доступной; отправлять новые сообщения после отвязки нельзя.
- Google receipt закрепляется за одним владельцем в отдельной таблице даже после смены тарифа. Проверяется внешний account identifier, если Google его возвращает. Google-платежи не включались.
- Приватные вложения обслуживаются API с проверкой владельца/участников и коротким токеном файла; переносится ранее подготовленная защита медиа. Прямое публичное чтение облачного бакета нужно выключить отдельно в его настройках.
- Блокировка строки тренера сериализует проверку квоты перед назначением клиента. Обработка изображения ограничена 20 мегапикселями перед декодированием полного изображения.
- Обновлены FastAPI, Starlette, python-multipart и Pillow. JWT переведён с python-jose на PyJWT, что убирает зависимость от python-ecdsa. Обновлены уязвимые glob/minimatch только в инструментах Expo через адресные overrides.
- Вход/восстановление не растягивают содержимое при прокрутке за верхнюю границу. Шапка не отрывается от области статусной строки.
- Ограничение тестового отправителя Resend распознаётся отдельно и показывается на выбранном языке без раскрытия адресов из ответа провайдера.

## Письма и восстановление

Письмо на адрес владельца Resend уже приходило по сообщению пользователя. Отказ при восстановлении на другой адрес соответствует ограничению `onboarding@resend.dev`: этот отправитель разрешён только для почты владельца Resend. Это ограничение сервиса нельзя убрать изменением приложения. Для остальных адресов нужен подтверждённый почтовый домен и `EMAIL_FROM` на нём. См. [документацию Resend](https://resend.com/docs/knowledge-base/403-error-resend-dev-domain).

И подтверждение, и восстановление используют Resend HTTPS при `EMAIL_PROVIDER=resend`. Ссылка `coachflow://reset-password` предназначена для установленной сборки приложения. В Expo Go собственная схема приложения не регистрируется: для проверки можно скопировать токен из письма в экран восстановления. Письмо содержит и ссылку, и токен. Нельзя подменять адрес получателя адресом владельца сервиса: это отправило бы чужой токен восстановления постороннему.

## Обновление существующего backend

Для выпуска используется согласованный backend-пакет с резервной копией базы. Нельзя публиковать один `auth.py` без остальных файлов и миграций. Фактическую ревизию запущенного сервера можно проверить по `revision` в `/health`.

1. Сохранить резервную копию PostgreSQL и проверить её восстановление. Проверить обновление на отдельной PostgreSQL с копией схемы: тесты SQLite не доказывают поведение конкурентных блокировок PostgreSQL.
2. Установить `backend/requirements.txt` в окружении новой версии.
3. Из `backend` выполнить `python -m app.db.preflight`. Команда не изменяет базу. Для неизвестной/непомеченной схемы она остановится: нельзя вслепую выполнять `alembic stamp head`.
4. На проверенной базе выполнить `alembic upgrade head` до запуска нового backend. Новые ревизии: `c62026102701` (история trial/веса), затем `c62026110401` (лимиты, сессии, привязка покупок). Они не удаляют таблицы пользователей или их аккаунты. При неоднозначной исторической привязке покупки миграция остановится вместо выбора случайного владельца.
5. Запустить новую версию, проверить `/health/db`, вход, подтверждение с кодом и паролем, refresh, выход, восстановление и приватные вложения. Обновить мобильный клиент вместе с backend: `/auth/verify-email` теперь требует `password`.

На пустой новой базе используется отдельная команда `python -m app.db.bootstrap`: она создаёт текущую схему и помечает ревизию в одной транзакции, отказываясь работать с существующими таблицами. Первая историческая baseline-миграция не изменялась.

## Проверки

Backend: `python -m unittest discover -s tests -q`, `python -m pip check`. Проверены Python 3.12 в чистом окружении и локальный Python 3.13. SQL миграций генерируется без подключения к рабочей БД. Реальные письма и платежи из тестов не отправляются.

Итог: 41 backend-тест, 13 frontend-тестов, TypeScript и ESLint затронутых файлов прошли; iOS export собран. Повторные `pip-audit` для requirements и `npm audit --omit=dev` не обнаружили известных уязвимостей. Это не результат полного lint всех прежних экранов приложения.

Перед выпуском резервная копия рабочей базы восстановлена в отдельную локальную PostgreSQL 18.6. Обе миграции успешно применены на восстановленной копии, количество строк старых таблиц и хеши паролей сохранены. На PostgreSQL также прошли конкурентные проверки refresh, лимитов попыток и владельца покупки, а также отзыв сессии при выходе.

Frontend: `npm run typecheck`, `npm run test:regressions`, проверка затронутых файлов ESLint и iOS export. React integration tests монтируют DataProvider и проверяют смену аккаунта, поздний ответ и обновление токена. Визуальную прокрутку и клавиатуру нужно дополнительно проверить на самом iPhone.

Аудиты зависимостей не являются гарантией отсутствия неизвестных уязвимостей. Ранее раскрытые API/SMTP-секреты требуется заменить в соответствующих сервисах; код не может сделать это за владельца аккаунтов.
